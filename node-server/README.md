# Entity JSON Suite — Node.js Server

High-performance static JSON file server for [entity_json_suite](../). Serves
files generated by the Drupal modules (`headless_entity_serializer` and
`entity_json_views`) directly from disk — without bootstrapping Drupal.

## Why

| | Drupal (`entity_json_serving`) | Node.js (this) |
|--|--|--|
| Latency | ~80-150ms (bootstrap) | ~3-10ms |
| Throughput | ~500 req/s | ~10,000 req/s |
| Alias resolution | `path_alias.manager` | File lookup in `alias-buckets/` |
| Resource cost | PHP-FPM worker per request | Single Node.js process |
| Scaling | Limited by PHP workers | Event-loop, horizontally scalable |
| Auth | Drupal permission | Manual (header, token, IP) |

The `entity_json_serving` Drupal module is kept as an alternative for
environments that don't want a Node.js dependency.

## Requirements

- Node.js 20+
- Files generated by Drupal's `headless_entity_serializer` and `entity_json_views`

## Installation

```bash
cd entity_json_suite/node-server
npm install
cp .env.example .env
# Edit .env to point EXPORT_DIR / VIEWS_DIR / ALIAS_DIR to your Drupal files
```

## Configuration

All configuration is via environment variables (see `.env.example`):

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `3000` | HTTP port |
| `HOST` | `0.0.0.0` | Bind address |
| `EXPORT_DIR` | `./public/serialized` | Path to entity JSON files |
| `VIEWS_DIR` | `./public/views` | Path to view exports |
| `ALIAS_DIR` | `./public/alias-buckets` | Path to alias mappings |
| `CACHE_MAX_AGE` | `3600` | `Cache-Control: max-age` value (seconds) |
| `CORS_ORIGIN` | `*` | CORS `Access-Control-Allow-Origin` |
| `LOG_LEVEL` | `info` | Pino log level |

The default paths match Drupal's `public://` stream wrapper default (the
project's `web/sites/default/files/` directory).

## Routes

### `GET /json/:type/:id/:lang`

Serves a single entity translation JSON file.

```
GET /json/node/1/en
GET /json/node/4523/es
```

Path layout: `<EXPORT_DIR>/<type>/<bucket>/<id>/<lang>.json`
where `bucket = floor(id / 1000)`.

- `200` with JSON content
- `304 Not Modified` on matching `If-None-Match`
- `404` if file doesn't exist
- `400` on invalid `id`

### `GET /json/views/:view/:display`

Serves an exported view JSON file (from `entity_json_views`).

```
GET /json/views/articles/rest_export_1
```

Path layout: `<VIEWS_DIR>/<view>/<display>.json`.

### `GET /json/path/{lang}/{alias}`

Resolves a path alias to its entity and serves the JSON file. The `*` is a
**wildcard** that captures the full alias including slashes, so multi-segment
aliases work transparently.

The language code is **required** and is the first segment of the URL.
This makes the URL self-describing and the lookup deterministic — there is
no ambiguity about which language will be returned.

```
GET /json/path/en/about-us
GET /json/path/es/hola-mundo/3
GET /json/path/en/products/shoes/running
GET /json/path/en-GB/about
```

The language code is validated against an ISO-like regex
(`^[a-z]{2,3}(-[A-Z]{2})?$`) before any filesystem access. This defends
against path traversal in the lang parameter. If validation fails, the
request returns `400 Bad Request`.

Resolution:

1. Validate the lang code (regex: `^[a-z]{2,3}(-[A-Z]{2})?$`).
2. Sanitize the alias (match Drupal's `AliasBucketManager::sanitizeAliasPath`).
3. Search `<ALIAS_DIR>/<lang>/<bucket>/<sanitizedAlias>/data.json` for that
   language only (no cross-language fallback).
4. Read `{"entityType":"...","entityId":"..."}` from the file.
5. Serve `<EXPORT_DIR>/<type>/<bucket>/<id>/<lang>.json`.

Response headers include:
- `X-Entity-Type`
- `X-Entity-Lang`
- `X-Entity-Id`

**Example: disambiguation between languages**

If the alias `about` exists in both English and Spanish:

```
GET /json/path/en/about  → English entity
GET /json/path/es/about  → Spanish entity
```

There is no "default language" fallback — the caller must always specify
the language explicitly. If the alias doesn't exist in the requested
language, the response is `404 Not Found` (not a fallback to another
language).

## Cache behavior

All responses include:

- `ETag` based on file `mtime` and `size` (e.g., `"1712345678-42"`).
- `Cache-Control: public, max-age=<CACHE_MAX_AGE>`.
- `Last-Modified` (handled by `@fastify/static`).

A request with matching `If-None-Match` returns `304 Not Modified` with no body.

## Running

```bash
# Production
npm start

# Development (auto-reload)
npm run dev

# Tests
npm test
```

## Deployment

Suggested process manager: `pm2`.

```bash
pm2 start index.js --name entity-json-server
pm2 save
pm2 startup
```

For maximum performance, place behind nginx (TLS termination, gzip, rate limit)
and let it proxy to the Node.js process.

## Tests

```bash
npm test             # run once
npm run test:watch   # watch mode
npm run test:coverage  # with coverage
npm run lint         # ESLint check
```

Tests use [Vitest](https://vitest.dev/) and the project follows ESLint
recommended rules. Coverage:

- `path-utils.js` — bucket math, sanitization, path building, langcode validation
- `etag.js` — ETag generation, `If-None-Match` matching
- `response.js` — shared HTTP response helper (200/304/404, cache headers)
- `alias-resolver.js` — bucket iteration, sanitization, multi-segment aliases
- `integration.test.js` — full HTTP routes via `Fastify.inject()` covering:
  - entity/view/alias serving
  - 200 / 304 / 400 / 404 responses
  - multi-segment aliases (`/json/path/es/hola/mundo`, `/json/path/en/a/b/c`)
  - language validation (returns 400 on invalid lang code)
  - bucket math across ID ranges
  - alias sanitization (path traversal prevention)

## Relationship with `entity_json_serving`

Both implementations are compatible — they read the same files. You can run
either or both (e.g., Drupal for `/admin/*` routes, Node.js for `/json/*`).
Pick based on your operational needs.
